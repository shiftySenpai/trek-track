# How it works

## Data sources

| | [AeroDataBox](https://aerodatabox.com/) | [adsb.fi](https://adsb.fi/) |
|---|---|---|
| Provides | schedule, status, terminal, gate, belt, delay, aircraft assignment | live position, altitude, speed, registration, type |
| Key | required (instance-wide, admin-set) | none |
| Cost | free tier ≈ 600 requests/month | free, personal non-commercial use |

Both are reached directly from the plugin's isolated server process. They are the only
two hosts it may contact — the runtime network guard is built from the
`http:outbound:<host>` permissions in the manifest, so anything else is blocked.

## Resolving the flight

The reservation gives an airline and a flight number. Turning that into something
queryable is less trivial than it looks:

- **IATA airline designators are two alphanumeric characters**, and roughly 40 % of
  them contain a digit — `F9` Frontier, `U2` easyJet, `6E` IndiGo, `W6` Wizz Air.
  Candidate splits of the typed string are scored, and a prefix that is a *known*
  airline code wins. `F9 1234`, `F91234`, a bare `1234` with the airline field set,
  and the ICAO form `FFT1234` all converge on the same flight.
- **Airline names are matched loosely** — exact, then spelling variants, then an
  aggressively stripped "core" name. `Delta Airlines`, `Delta Air Lines`,
  `Delta Air Lines, Inc.` and `Delta` all reach `DL`.
- **Ambiguity is refused, not guessed.** Where a name is claimed by more than one
  carrier and no source settles it, no code is emitted. A wrong code returns someone
  else's flight, which is worse than an empty widget.

The dataset is generated by `npm run build:airlines` from
[Virtual Radar Server standing-data](https://github.com/vradarserver/standing-data)
(CC0, pinned to a commit) merged with [OpenFlights](https://github.com/jpatokal/openflights),
plus a hand-verified override layer in `server/data/airline-overrides.json`. The build
asserts a probe list of 58 known codes and **fails rather than shipping a wrong one** —
OpenFlights alone still maps `IndiGo` to `I9`, a defunct US carrier.

## Time handling

TREK reservation times are naive local times at the departure airport — no offset is
stored. The plugin therefore treats them as an **estimate** with a known ±14 h bound
and widens its fetch windows accordingly. As soon as a status lookup succeeds, the
authoritative UTC instants from AeroDataBox replace the estimate for the countdown,
the phase and the polling cadence.

This matters for correctness, not just tidiness: a live position is only shown when
the *authoritative* schedule agrees the aircraft could be up. Otherwise a flight
departing tomorrow would display the aircraft flying today's rotation.

## Quota

The free AeroDataBox tier is about **600 requests per month**, so the plugin budgets
deliberately:

**Fetch windows** — schedule is queried from 48 h before departure until 6 h after
arrival. The live position is fetched only when the flight is plausibly airborne, or
whenever the date-pinned status itself reports it en route.

**Cache TTL follows time-to-departure**, not a coarse phase:

| State | Refresh |
|---|---|
| Airborne, or within 3 h of departure | 1 min |
| 3–12 h out | 5 min |
| 12–48 h out | 30 min |
| Beyond 48 h | 2 h |
| Past | 6 h |

**Client polling** pauses while the tab is hidden and stops once every leg has
arrived. Multi-leg itineraries are fetched sequentially, not in parallel, to respect
both APIs' ~1 request/second ceiling.

Responses are cached per reservation, so several people viewing the same trip share
one lookup.

## Access control

The plugin's SQLite database is a single shared file with no per-user scoping, and
TREK reservation ids are sequential integers. `ctx.trips` is the only host surface
that membership-checks a read, so **every route goes through it before touching
storage** — deliberately without error-swallowing, so a rejection surfaces as `403`
rather than becoming a successful request. A reservation absent from the trip returns
`404`, identical to the non-member case, so membership cannot be probed by comparing
responses.

The userless hooks (trip warnings, map markers, PDF, calendar) *cannot* check
anything — they get no acting user. That is why the trust decision is made on the
write side: only the verified trip id is ever persisted, so those hooks can only
render rows a member actually caused.

The booking reference (PNR) is deliberately **not** included in the payload — it is
bearer-ish for airline "manage my booking" portals.

## What the plugin cannot do

Worth knowing before filing a feature request — these are platform limits, not
oversights:

- **No background push.** A userless job may not send notifications, so alerts fire
  while TREK is open or the trip is viewed.
- **No route line on TREK's own trip map.** The marker hook returns markers; there is
  no polyline field. The plugin draws the route in its own bundled map instead.
- **No external images, fonts or map tiles.** The UI runs at an opaque origin under a
  strict CSP. The world map is inline SVG for exactly this reason.
- **The widget cannot write to `ctx.config`.** It is read-only, which is why an
  in-widget key is stored separately — and why the config API takes precedence.

## Calendar events need a key

Calendar entries are built only from authoritative UTC times returned by a status
lookup. A keyless instance therefore produces none, and a flight further out than the
status window produces none until it comes into range. This is deliberate: an event
built from the reservation's naive local time could be hours off, and a wrong calendar
entry is worse than a missing one.
